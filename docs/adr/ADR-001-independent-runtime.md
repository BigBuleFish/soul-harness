# ADR-001 — 取消插件内核，采用独立常驻 Harness

- **状态**：已接受（Accepted）
- **日期**：2026-11-15
- **决策者**：wblnn（项目所有者）
- **关联**：SH-001 · `docs/migration/LEGACY-BASELINE.md`

---

## 1. 背景

现有 `dsh-soul-core` 是 DSH 插件。人格状态虽已落盘（`~/.dsh/soul`），但：

- 生命周期绑在宿主进程上，DSH 不跑，人格就不存在；
- 主观状态写入没有单一协调者，`lib/index.js` 用进程全局变量做中转；
- 表结构与宿主工具（`soul_block` 注入、19 个工具、`/dsh-soul/api/*`）缠绕；
- 缺少真实遗忘、并行思维、睡眠/梦境的物理隔离条件。

要的是"人格状态独立于模型、会话和宿主"。这四条与插件形态直接冲突，改不出来，只能换形态。

## 2. 决策

**新内核为独立常驻 Daemon，DSH 降级为可选 Adapter。** 具体：

| # | 决策 | 理由 |
|---|---|---|
| D1 | 新代码落在**独立仓库** `F:\6\Soul_Harness_2.0`（`main` 分支） | 与冻结的旧插件完全隔离；旧仓库保留为迁移对照与 Adapter 源 |
| D2 | 运行时基线为 **Node.js 24 LTS**，`engines.node` 为 `>=24.15.0 <25`，精确版本以实测锁定（见 `PLAN.md` C1），不升 26.x | 本地只装了 24；跨大版本升级与 P0 冻结同时进行会引入无法归因的故障 |
| D3 | 语言 **TypeScript**，包管理 pnpm，构建 Turborepo | 双 AI 协作需要类型与契约约束；纯 JS 无法表达跨模块协议 |
| D4 | 权威存储 **SQLite WAL**，单写入协调器 | 单机单人格场景足够；WAL 写并发可用，但**写入者只有一个** |
| D5 | 线协议字段 **camelCase**（与 111.md 的 TS 接口一致），数据库列名 **snake_case**，映射由 **`packages/persistence`** 负责 | `contracts` 只定义协议与 Schema，不应知道数据库列名；把映射放在持久层是唯一不会产生循环依赖的位置 |
| D6 | 第一版**不引入 Drizzle**，用 `node:sqlite` + 薄仓储层 | 单写入器、epoch 校验、事务边界需要看清 SQL；ORM 会把这些藏起来，而它们正是 P0 安全约束所在。Studio 只读查询可另议 |
| D7 | 文档用**中文**，代码注释用**英文** | 两个 AI 都读中文计划，但代码注释混写会产生风格漂移 |
| D8 | 首期**单 SQLite 文件 + 逻辑隔离**（表归属 + 接口边界）。**P1 不声称具备物理隔离**；Archive / Action Gateway / Dream Sandbox 达到门槛前一律不启用 | 物理四库是实现细节，但"宣称已隔离"与"实际同库"不能并存。先承认边界不足，再按门槛逐项升级（门槛见 `PLAN.md` §6.2） |

## 3. 后果

**正面**

- Daemon 可脱离 DSH 独立启停，人格连续性不再依赖宿主。
- 旧插件冻结在 `legacy-plugin-frozen-2026-11-15`，随时可作行为对照与数据源。
- 类型 + Schema 双重约束，两个 AI 的产出能自动对齐，而不是靠口头约定。

**代价与风险**

- 迁移成本真实存在：旧库 13611 条 events、2025 条 links 需要一次性重编码，**不是导出导入**。
- 旧库 `user_version=0`，无迁移版本号，迁移器只能靠表结构探测判断源 schema。
- 两套代码并存期间，"哪个是权威"必须由文档和端口约定保证，不能靠人记。
- **P1 阶段不存在物理隔离。** 所有三域数据同库同进程，安全承诺仅靠接口与代码约束。
  因此 P1 只允许运行不产生跨域安全承诺的功能；需要物理隔离的能力必须等门槛达成（`PLAN.md` §6.2）。
  这一点已在 SH-002 审查中确认并写入文档，早期版本"首期单库 + 进程分离 + 文件权限"的自相矛盾表述已废止。
- Node 24 与历史 DOCX 写的 26.x 不一致。已在 `PLAN.md` §5.2 的 C1 统一为 Node 24 LTS，历史文档仅归档不再修订。

## 4. 被否决的备选

| 方案 | 否决理由 |
|---|---|
| 继续做 DSH 插件 | 生命周期、权限隔离、状态权威三项都不满足；长期改造成本更高 |
| 起步即微服务 | 分布式事务与调试开销远大于收益；单机单人格没有这个必要 |
| 在旧仓库里开 `soul-harness/` 子目录 | 两套 `package.json`、CI 与 release 语义纠缠；旧仓库的冻结承诺会被稀释 |
| Rust 全重写 | 调试成本高，且不直接提升记忆与认知质量；保留为后续热点优化选项 |

## 5. 落地约束（对后续所有任务生效）

1. 新内核代码**不得** `import` 任何 `@deepseek-ai/*` 包。
2. 新内核代码**不得**假设存在 DSH 会话、`soul_block` 变量或宿主工具注册表。
3. 任何"为了让 DSH 用起来"的适配逻辑，只能写在 `adapters/dsh/`。
4. 旧仓库的 `main` 不接受认知引擎相关提交。
5. 技术栈变更需新开 ADR；不得在实现任务里顺手升级基础依赖。
